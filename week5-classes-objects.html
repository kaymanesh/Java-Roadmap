کلاس و شیء (Class & Object)

پایه و اساس تمام برنامه‌نویسی شیءگرا

چرا به شیءگرایی نیاز داریم؟

فرض کنید می‌خواهید یک سیستم مدیریت فروشگاه بنویسید. در هفته‌های گذشته، برای ذخیره اطلاعات یک محصول باید چند متغیر جداگانه مثل productName، productPrice و productStock می‌ساختید. اگر فروشگاه ۱۰۰ محصول داشت، مدیریت ۳۰۰ متغیر پراکنده تقریباً غیرممکن می‌شد.

برنامه‌نویسی شیءگرا (OOP) راه‌حل این مشکل است. در این روش، داده‌ها (مثل نام و قیمت) و رفتارهای مرتبط با آن‌ها (مثل افزایش موجودی یا اعمال تخفیف) را در یک بسته واحد به نام کلاس کنار هم قرار می‌دهیم. سپس از روی این کلاس، نمونه‌های واقعی به نام شیء می‌سازیم.

تعریف ساده کلاس و شیء کلاس (Class) مثل یک نقشه ساختمان یا قالب شیرینی‌پزی است. خودش یک موجودیت واقعی نیست، بلکه مشخص می‌کند شیءهای ساخته‌شده از آن چه ویژگی‌ها و رفتارهایی خواهند داشت.
شیء (Object) نمونه واقعی و قابل استفاده‌ای است که از روی آن نقشه ساخته می‌شود. هر شیء داده‌های مخصوص به خودش را دارد.

ساختار یک کلاس در جاوا

یک کلاس معمولاً شامل فیلدها (Fields) برای نگهداری داده و متدها (Methods) برای انجام رفتارهاست.

Java — تعریف کلاس و ساخت شیء 
class Car {
    String model;
    int speed;

    void accelerate(int amount) {
        speed += amount;
    }
}

public class CarDemo {
    public static void main(String[] args) {
        Car pride = new Car(); // ساخت شیء
        pride.model = "Pride";
        
        Car peugeot = new Car(); // ساخت شیء دوم
        peugeot.model = "Peugeot";

        pride.accelerate(20);
        peugeot.accelerate(35);
        
        System.out.println(pride.model + ": " + pride.speed);
        System.out.println(peugeot.model + ": " + peugeot.speed);
    }
}
نکته درباره new کلمه کلیدی new مسئول ساخت فضای جدید در حافظه و ساختن یک شیء واقعی است. تا زمانی که از new استفاده نکنید، متغیر شما فقط یک ارجاع خالی است.

حافظه، Stack، Heap و انواع ارجاعی

درک تفاوت ارجاع و مقدار در حافظه

RAM، Stack و Heap به زبان ساده

وقتی برنامه‌ای در حال اجراست، از حافظه اصلی سیستم (RAM) استفاده می‌کند. برای اینکه مدیریت داده‌ها ساده‌تر شود، جاوا این حافظه را به دو بخش مفهومی تقسیم می‌کند:

  • Stack (پشته): بخش سریع و منظمی که متغیرهای محلی (Local Variables) و اطلاعات مسیر اجرای متدها را نگه می‌دارد. متغیرهای اولیه (Primitive) مقدار واقعی خود را مستقیماً در Stack نگه می‌دارند.
  • Heap (کپه): بخش بزرگ‌تری که شیءهای ساخته‌شده با new در آن قرار می‌گیرند. متغیرهای ارجاعی (Reference) در Stack قرار دارند اما مقدار آن‌ها یک آدرس است که به شیء در Heap اشاره می‌کند.

تفاوت Primitive و Reference

در هفته دوم با انواع داده اولیه مثل int و double آشنا شدید. این‌ها داده را مستقیماً نگه می‌دارند. اما کلاس‌ها (مثل String یا کلاس‌هایی که خودتان می‌سازید) انواع ارجاعی هستند.

ویژگی نوع اولیه (Primitive) نوع ارجاعی (Reference)
نمونه‌هاint، double، booleanString، کلاس‌های ساخته‌شده، آرایه‌ها
محل ذخیرهمستقیماً در Stackآدرس در Stack، شیء در Heap
عملگر =کپی مقدار واقعیکپی آدرس (اشاره به همان شیء)
مقدار پیش‌فرض0، 0.0، falsenull

مثال عملی: کپی کردن مقدار در برابر کپی کردن ارجاع

Java 
int a = 10;
int b = a;    // کپی مقدار: b یک 10 مستقل است
b = 99;
System.out.println(a); // خروجی: 10

Car first = new Car();
first.model = "Pride";
Car second = first; // کپی ارجاع: هر دو به یک شیء اشاره می‌کنند
second.model = "Peugeot";
System.out.println(first.model); // خروجی: Peugeot

null و خطای NullPointerException

مقدار null یعنی متغیر ارجاعی شما به هیچ شیئی در حافظه اشاره نمی‌کند. این با یک رشته خالی ("") یا عدد صفر کاملاً متفاوت است.

NullPointerException اگر سعی کنید به فیلد یا متدی از یک شیء دسترسی پیدا کنید در حالی که آن شیء null است، برنامه با خطای زمان اجرای NullPointerException متوقف می‌شود. این یکی از رایج‌ترین خطاهای برنامه‌نویسان در تمام سطوح است.
Java 
Car myCar = null;
System.out.println(myCar.model); // خطا: NullPointerException

// راه صحیح:
if (myCar != null) {
    System.out.println(myCar.model);
}

سازنده‌ها (Constructors) و کلمه کلیدی this

مقداردهی اولیه شیء از لحظه تولد

سازنده چیست؟

فرض کنید یک کلاس Student دارید. وقتی می‌نویسید new Student()، جاوا باید بداند نام دانشجو و سن او را از کجا بیاورد. سازنده یک متد ویژه است که دقیقاً در لحظه ساخت شیء با new اجرا می‌شود و وظیفه آن مقداردهی اولیه فیلدهاست.

سه ویژگی مهم سازنده ۱. نام سازنده باید دقیقاً برابر با نام کلاس باشد (با همان حروف بزرگ و کوچک).
۲. سازنده هیچ نوع بازگشتی ندارد (حتی void هم نمی‌نویسیم).
۳. به‌طور خودکار هنگام ساخت شیء با new فراخوانی می‌شود.

سازنده پیش‌فرض در برابر سازنده پارامتردار

اگر شما هیچ سازنده‌ای در کلاس تعریف نکنید، جاوا یک سازنده پیش‌فرض (بدون پارامتر) به‌طور خودکار در اختیار شما قرار می‌دهد که هیچ کاری انجام نمی‌دهد. اما اگر خودتان حتی یک سازنده پارامتردار بنویسید، سازنده پیش‌فرض حذف می‌شود.

Java 
class Student {
    String name;
    int age;

    // سازنده بدون پارامتر (پیش‌فرض دستی)
    Student() {
        this("Unknown", 18);
    }

    // سازنده پارامتردار
    Student(String name, int age) {
        this.name = name;
        this.age = age;
    }
}

کلمه کلیدی this

وقتی پارامترهای یک سازنده با نام فیلدهای کلاس هم‌نام باشند (مثل name و name)، جاوا نمی‌داند کدام را باید مقداردهی کند. کلمه کلیدی this به معنای «همین شیء فعلی» است. با نوشتن this.name به فیلد کلاس اشاره می‌کنیم و با نوشتن name ساده به پارامتر ورودی.

نکته استفاده از this همیشه اجباری نیست. اگر نام پارامترها را متفاوت انتخاب کنید (مثلاً newName) نیازی به this نیست، اما در پروژه‌های واقعی استفاده از this برای خوانایی بیشتر و جلوگیری از ابهام بسیار رایج است.

سربارگذاری سازنده (Constructor Overloading)

ساخت شیء با مسیرهای مختلف

چرا به چند سازنده نیاز داریم؟

گاهی می‌خواهید یک شیء را با داده‌های کامل بسازید، گاهی فقط با نام، و گاهی بدون هیچ داده‌ای (مثلاً یک شیء خالی). جاوا اجازه می‌دهد چندین سازنده با نام یکسان در یک کلاس داشته باشید، به شرطی که لیست پارامترهای آن‌ها (تعداد یا نوع) متفاوت باشد.

Java 
class Product {
    String name;
    double price;

    Product() {
        this("Unknown", 0.0);
    }

    Product(String name) {
        this(name, 0.0);
    }

    Product(String name, double price) {
        this.name = name;
        this.price = price;
    }
}

فراخوانی سازنده دیگر با this(...)

در مثال بالا، سازنده بدون پارامتر با نوشتن this("Unknown", 0.0) سازنده پارامتردار را صدا می‌زند. این کار از تکرار کد جلوگیری می‌کند. نکته مهم این است که اگر از this(...) استفاده می‌کنید، باید اولین دستور در بدنه سازنده باشد.

خطاهای رایج در سربارگذاری فقط تغییر نام پارامترها (مثلاً int a به int b) برای سربارگذاری کافی نیست و خطای کامپایل می‌دهد. همچنین فقط تغییر نوع بازگشتی (که سازنده اصلاً ندارد) مجاز نیست.
۵

کپسوله‌سازی (Encapsulation) و private

محافظت از داده‌ها در برابر دستکاری‌های ناخواسته

کپسوله‌سازی چیست؟

تصور کنید یک حساب بانکی دارید. اگر تمام اطلاعات و موجودی حساب به‌صورت عمومی در دسترس باشد، هر کسی می‌تواند موجودی را بدون واریز کردن پول، دستکاری کند! کپسوله‌سازی یعنی پنهان کردن داده‌های حساس داخلی و اجازه دادن به دنیای بیرون که فقط از طریق راه‌های مشخص و کنترل‌شده (متدها) با این داده‌ها تعامل کند.

تعریف کپسوله‌سازی اولین ستون OOP است و به معنای بسته‌بندی داده‌ها (فیلدها) و رفتارها (متدها) در یک واحد (کلاس) و محدود کردن دسترسی مستقیم به داده‌ها از خارج کلاس است.

تعیین‌کننده‌های دسترسی (Access Modifiers)

جاوا چهار سطح دسترسی اصلی دارد، اما تمرکز ما در این هفته روی دو مورد اصلی است:

  • public: همه‌جا قابل دسترسی است (مثل درِ ورودی مغازه).
  • private: فقط داخل همان کلاس قابل دسترسی است (مثل گاوصندوق مغازه).
  • protected: همان پکیج و کلاس‌های فرزند (در هفته‌های بعد توضیح داده می‌شود).
  • Default (بدون کلمه کلیدی): فقط در همان پکیج قابل دسترسی است.
Java — دسترسی مستقیم ممنوع! 
class BankAccount {
    private double balance; // فقط داخل این کلاس قابل دسترسی است

    BankAccount(double initial) {
        if (initial >= 0) {
            this.balance = initial;
        }
    }
}

class Demo {
    public static void main(String[] args) {
        BankAccount acc = new BankAccount(100);
        // acc.balance = -500; // خطای کامپایل! دسترسی غیرمجاز
    }
}
نکته مهم private کردن فیلدها به‌تنهایی کافی نیست. اگر برای تغییر آن‌ها هیچ راهی نگذارید، شیء شما بی‌فایده می‌شود. راه صحیح، ساختن متدهای Getter و Setter است.
۶

متدهای Getter و Setter

پل‌های ارتباطی امن با داده‌های خصوصی

Getter و Setter چه کاری انجام می‌دهند؟

متدهای Getter (گیرنده) برای خواندن مقدار یک فیلد خصوصی استفاده می‌شوند. متدهای Setter (تنظیم‌کننده) برای تغییر مقدار آن به کار می‌روند. Setterها این امکان را به ما می‌دهند که قبل از ذخیره مقدار جدید، آن را بررسی کنیم (اعتبارسنجی یا Validation).

قرارداد نام‌گذاری استاندارد

در جاوا، استاندارد (JavaBeans) این است که نام Getter با get شروع شود و نام فیلد با حرف بزرگ ادامه یابد (مثلاً getName). برای فیلدهای boolean از is استفاده می‌شود (مثلاً isActive). Setterها با set شروع می‌شوند (مثلاً setName).

Java — کپسوله‌سازی کامل 
class Student {
    private String name;
    private int age;

    Student(String name, int age) {
        this.name = name;
        setAge(age); // استفاده از متد برای اعتبارسنجی حتی در سازنده
    }

    // Getter
    public String getName() {
        return name;
    }

    public int getAge() {
        return age;
    }

    // Setter با اعتبارسنجی
    public void setName(String name) {
        if (name != null && !name.isBlank()) {
            this.name = name;
        }
    }

    public boolean setAge(int age) {
        if (age < 0 || age > 120) {
            return false; // رد کردن مقدار نامعتبر
        }
        this.age = age;
        return true;
    }
}
Setter همیشه لازم نیست اگر قرار نیست یک فیلد بعد از ساخت شیء تغییر کند (مثل شماره حساب بانکی)، نیازی به Setter برای آن نیست. فقط Getter کافی است تا شیء شما «فقط‌خواندنی» (Read-only) شود.

تمرین‌ها و پروژه‌های عملی

تثبیت مفاهیم با چالش‌های واقعی

پروژه کارگاهی

سیستم حساب بانکی (BankAccount)

یک کلاس BankAccount طراحی کنید. فیلدها باید شامل شماره حساب (String)، نام صاحب حساب (String) و موجودی (double) باشند. همه فیلدها باید کپسوله (private) شوند. متد deposit(double amount) برای واریز و withdraw(double amount) برای برداشت بنویسید.

قوانین منطقی
  1. موجودی حساب هرگز نباید منفی شود.
  2. مبلغ واریز باید بزرگ‌تر از صفر باشد.
  3. مبلغ برداشت نباید بیشتر از موجودی فعلی باشد.
راهنمای گام‌به‌گام
  1. ۱
    کلاس را با سه فیلد private تعریف کنید. برای موجودی یک Getter بسازید اما Setter نگذارید (تا از بیرون مستقیماً تغییر نکند).
  2. ۲
    یک سازنده (Constructor) بنویسید تا هنگام ساخت حساب، شماره حساب و نام مالک مشخص شوند و موجودی اولیه صفر یا مقدار معتبر داده شود.
  3. ۳
    در متد deposit، ابتدا بررسی کنید که آیا مبلغ بزرگ‌تر از صفر است یا خیر. اگر بود، به موجودی اضافه کنید.
  4. ۴
    در متد withdraw، ابتدا بررسی کنید که مبلغ بزرگ‌تر از صفر و کوچک‌تر یا مساوی موجودی باشد. در صورت موفقیت، مبلغ را از موجودی کم کنید.
  5. ۵
    در متد main یک شیء بسازید، چند واریز و برداشت انجام دهید و سعی کنید با برداشت بیش از حد، سیستم را به چالش بکشید.
اشتباهات رایج
  • فراموش کردن بررسی منفی بودن: اگر مبلغ ورودی منفی باشد، در متد deposit موجودی کم می‌شود. حتماً شرط amount > 0 را بگذارید.
  • اجازه برداشت بیش از موجودی: اگر موجودی ۵۰ است و کاربر درخواست برداشت ۱۰۰ می‌کند، برنامه نباید موجودی را ۵۰- کند.
  • تنظیم مستقیم موجودی در main: اگر برای موجودی Setter بگذارید، کد بیرونی می‌تواند قانون را دور بزند. فقط Getter بگذارید و تغییرات را از طریق deposit/withdraw انجام دهید.
تمرین منزل ۱

طراحی کلاس محصول (Product)

برای یک فروشگاه اینترنتی یک کلاس Product بسازید. ویژگی‌ها شامل شناسه (int)، نام (String)، قیمت (double) و موجودی انبار (int) است. تمام فیلدها کپسوله شوند. متدهایی برای افزایش موجودی و اعمال تخفیف درصدی روی قیمت بنویسید.

راهنمای گام‌به‌گام
  1. ۱
    کلاس را با فیلدهای private تعریف کرده و برای همه Getter بگذارید. برای قیمت و موجودی Setter مستقیم نگذارید.
  2. ۲
    متد increaseStock(int amount) بسازید که فقط مقادیر مثبت را قبول کند و به موجودی اضافه کند.
  3. ۳
    متد applyDiscount(double percent) بسازید. بررسی کنید درصد بین ۰ تا ۱۰۰ باشد. سپس قیمت جدید را محاسبه کنید: price = price - (price * percent / 100).
  4. ۴
    در main یک شیء بسازید و سناریوهای مختلف (درصد منفی، درصد بالای ۱۰۰) را تست کنید.
اشتباهات رایج
  • تخفیف نامعتبر: اگر درصد تخفیف ۱۵۰ باشد، قیمت منفی می‌شود. حتماً محدوده را چک کنید.
  • استفاده از Setter برای قیمت: اگر Setter عمومی بگذارید، کاربر می‌تواند قیمت را دستی به ۰ تغییر دهد. تغییر قیمت فقط باید از طریق متد تخفیف باشد.
  • عدم بررسی ورودی موجودی: افزایش موجودی با عدد منفی در واقع یعنی کاهش موجودی. باید جلوی آن گرفته شود.
تمرین منزل ۲

کپی ارجاع و بررسی حافظه

یک کلاس ساده Book با فیلدهای title و author بسازید. دو شیء متفاوت بسازید. سپس ارجاع شیء دوم را به یک متغیر سوم بدهید و از طریق متغیر سوم، عنوان را تغییر دهید. با چاپ مقادیر، ثابت کنید که شیء دوم تغییر کرده اما شیء اول دست‌نخورده مانده است.

راهنمای گام‌به‌گام
  1. ۱
    کلاس Book را با فیلدهای public (برای ساده‌تر بودن این تمرین خاص) بسازید.
  2. ۲
    در main دو شیء b1 و b2 بسازید و عنوان‌های متفاوت بدهید.
  3. ۳
    متغیر b3 = b2 را تعریف کنید.
  4. ۴
    مقدار b3.title را تغییر دهید.
  5. ۵
    عنوان b1 و b2 را چاپ کنید و ببینید که b2 تغییر کرده ولی b1 نه. دلیل آن را بر اساس Stack و Heap توضیح دهید.
تمرین منزل ۳

شکار خطای NullPointerException

برنامه‌ای بنویسید که یک شیء از کلاس Student را تعریف کند اما آن را با new نسازد (یعنی null باشد). سپس سعی کنید نام آن را چاپ کنید تا خطا را ببینید. سپس برنامه را طوری اصلاح کنید که خطا رخ ندهد و پیام مناسبی چاپ شود.

راهنمای گام‌به‌گام
  1. ۱
    کلاس Student را با یک فیلد name بسازید.
  2. ۲
    در main بنویسید: Student s = null; و سپس System.out.println(s.name);
  3. ۳
    برنامه را اجرا کنید و پیام خطا را در کنسول ببینید (Stack Trace).
  4. ۴
    کد را اصلاح کنید: یک شرط if (s != null) اضافه کنید یا شیء را با new Student() مقداردهی کنید.
تمرین منزل ۴

مقایسه سربارگذاری سازنده

کلاسی به نام Course طراحی کنید که سه سازنده داشته باشد: یکی بدون پارامتر (نام: "نامشخص")، یکی فقط با نام درس، و یکی با نام و تعداد واحدها. با استفاده از this(...) از تکرار کد جلوگیری کنید. هر سه حالت را در main تست کنید.

راهنمای گام‌به‌گام
  1. ۱
    کلاس را با فیلدهای name و credits تعریف کنید.
  2. ۲
    سازنده سه‌پارامتری را به‌عنوان سازنده اصلی بنویسید که مقادیر را تنظیم می‌کند.
  3. ۳
    در سازنده تک‌پارامتری بنویسید: this(name, 3) (۳ واحد پیش‌فرض).
  4. ۴
    در سازنده بدون پارامتر بنویسید: this("نامشخص", 0).
تمرین منزل ۵

فقط‌خواندنی کردن داده‌ها (Read-Only)

کلاسی برای یک کارمند (Employee) طراحی کنید که شماره پرسنلی او پس از ساخت هرگز نباید تغییر کند. برای شماره پرسنلی فقط Getter بگذارید و هیچ Setter ننویسید. متد main را طوری بنویسید که ثابت کند امکان تغییر مستقیم وجود ندارد.

راهنمای گام‌به‌گام
  1. ۱
    فیلد employeeId را private تعریف کنید.
  2. ۲
    در سازنده، مقدار آن را تنظیم کنید.
  3. ۳
    متد Getter بسازید اما Setter نگذارید.
  4. ۴
    در main تلاش کنید مقدار فیلد را تغییر دهید و ببینید که کامپایلر خطا می‌دهد.
۸

پرسش و پاسخ

پاسخ به ابهامات رایج دانشجویان

پرسش: تفاوت دقیق بین کلاس و شیء چیست؟

پاسخ: کلاس یک «نقشه» یا قالب است. خودش در حافظه RAM شیء واقعی ندارد. شیء «نمونه» ساخته‌شده از روی آن نقشه است که دارای فضای واقعی در حافظه (Heap) است. شما می‌توانید از روی یک کلاس، هزاران شیء با ویژگی‌های متفاوت بسازید.

پرسش: آیا هر کلاس حتماً باید سازنده داشته باشد؟

پاسخ: خیر. اگر شما هیچ سازنده‌ای ننویسید، جاوا به‌طور خودکار یک «سازنده پیش‌فرض» بدون پارامتر برای شما می‌سازد که فیلدها را با مقادیر پیش‌فرض (مثل 0 و null) پر می‌کند. اما اگر خودتان یک سازنده بنویسید، دیگر خبری از سازنده پیش‌فرض خودکار نیست.

پرسش: چرا باید از private استفاده کنیم؟ مگر public راحت‌تر نیست؟

پاسخ: public راحت است اما خطرناک. اگر فیلدی public باشد، هر بخشی از برنامه می‌تواند مقدار نامعتبر به آن بدهد (مثلاً سن منفی). با private کردن فیلد و استفاده از Setter، شما کنترل می‌کنید که فقط داده‌های صحیح و منطقی وارد شیء شوند.

پرسش: چرا وقتی اینتلیجی می‌گوید getAge، من باید تایپ کنم؟ نمی‌شود فیلد را public کرد؟

پاسخ: در محیط‌های توسعه مثل IntelliJ، با زدن کلیدهای میانبر (Alt+Insert) می‌توانید تمام Getter و Setterها را در یک ثانیه تولید کنید. پس تایپ دستی لازم نیست. مزیت بزرگ Getter و Setter این است که بعداً می‌توانید درون آن‌ها منطق (مثل اعتبارسنجی یا لاگ‌گذاری) اضافه کنید بدون اینکه کدهای بیرونی به‌هم بریزند.

پرسش: تفاوت this.name و name در یک متد چیست؟

پاسخ: this.name به فیلد (متغیر عضو) کلاس اشاره می‌کند. name ساده به متغیر محلی (پارامتر) اشاره می‌کند. وقتی نام پارامتر با نام فیلد یکی باشد، برای جلوگیری از سردرگمی و مقداردهی درست، باید از this استفاده کنید.

پرسش: اگر یک شیء را برابر null بگذارم، آیا آن شیء از حافظه پاک می‌شود؟

پاسخ: شما فقط ارتباط متغیر خود را با شیء قطع کرده‌اید. شیء در حافظه Heap باقی می‌ماند تا زمانی که Garbage Collector (زباله‌روب جاوا) آن را پیدا کرده و فضای حافظه را آزاد کند. این فرآیند خودکار است و شما نیازی به مدیریت دستی حافظه ندارید.

پرسش: آیا سازنده‌ها می‌توانند private باشند؟

پاسخ: بله. اگر سازنده‌ای private باشد، فقط خود کلاس می‌تواند از آن استفاده کند و کدهای بیرونی نمی‌توانند مستقیماً شیء بسازند. این تکنیک در الگوی طراحی Singleton (ساخت تنها یک نمونه از کلاس) بسیار استفاده می‌شود.

پرسش: چرا کلاس String در جاوا با اینکه ارجاعی است، مثل نوع اولیه رفتار می‌کند؟

پاسخ: String در جاوا یک کلاس تغییرناپذیر (Immutable) است و در String Pool نگهداری می‌شود. این طراحی خاص باعث می‌شود جاوا بتواند در مصرف حافظه صرفه‌جویی کند. اما همچنان یک نوع ارجاعی است و با null برابر می‌شود و در Heap نگه داشته می‌شود.

پرسش: اگر برای فیلدی هم Getter بگذارم هم Setter، آیا هنوز کپسوله‌سازی محسوب می‌شود؟

پاسخ: بله، اما کیفیت آن پایین است. کپسوله‌سازی واقعی یعنی کنترل. اگر Getter و Setter بدون هیچ منطق و اعتبارسنجی باشند، در واقع همان دسترسی مستقیم public را شبیه‌سازی کرده‌اید با کد اضافه. بهترین کار این است که در Setter منطق مناسب (مثل بررسی محدوده) بگذارید.

پرسش: چه زمانی باید از Setter استفاده نکنم و فیلد را فقط‌خواندنی بگذارم؟

پاسخ: هر زمان که داده هویتی و شناسایی‌کننده باشد (مثل شماره حساب بانکی، کد ملی، شماره پرسنلی، تاریخ تولد). این داده‌ها نباید پس از ساخته شدن شیء تغییر کنند، بنابراین فقط Getter گذاشتن و پرهیز از Setter طراحی ایمن‌تری است.

جمع‌بندی و نکات کلیدی

مرور فشرده هفته پنجم

کلاس و شیء

  • کلاس نقشه (Blueprint) و شیء نمونه واقعی ساخته‌شده از روی آن است.
  • شیءها با استفاده از کلمه کلیدی new در حافظه Heap ساخته می‌شوند.
  • هر شیء دارای وضعیت مستقل خود است، حتی اگر از یک کلاس باشند.

حافظه و ارجاع‌ها

  • انواع داده اولیه (int, double) مقدار خود را در Stack نگه می‌دارند.
  • انواع داده ارجاعی (کلاس‌ها) آدرس شیء در Stack و خود شیء را در Heap نگه می‌دارند.
  • null به معنای نبودن ارجاع است و دسترسی به فیلد آن باعث NullPointerException می‌شود.

سازنده‌ها (Constructors)

  • متدی ویژه برای مقداردهی اولیه است، هم‌نام کلاس است و نوع بازگشتی ندارد.
  • با استفاده از this() می‌توان از یک سازنده دیگر در همان کلاس استفاده کرد تا کد تکراری کاهش یابد.
  • سربارگذاری سازنده یعنی چند سازنده با پارامترهای متفاوت.

کپسوله‌سازی

  • پنهان کردن داده‌ها با کلمه کلیدی private برای جلوگیری از دسترسی مستقیم.
  • استفاده از متدهای Getter برای خواندن و Setter برای تغییر کنترل‌شده.
  • Setterها باید شامل منطق اعتبارسنجی (Validation) باشند تا از خراب شدن وضعیت شیء جلوگیری شود.
  • همه فیلدها نیاز به Setter ندارند (فیلدهای فقط‌خواندنی).
